# 발행이 끊길 때 — 환경 쪽 원인 대응서

> 이 문서는 **킷의 결함이 아닌 것**을 다룬다. 킷의 도구·게이트는 멀쩡한데 발행만
> 안 되는 상황, 즉 그 기기와 망에서 오는 실패가 대상이다. 킷 자체의 게이트 실패는
> `templates/publish-checklist.md`, 설치 단계 실패는 `SETUP.md` 를 본다.
>
> 근거는 2026-08-14~16 맥 워커 실측(이슈 #33·#37·#38·#39)이다. 여기 적힌 수치는
> **그 기기의 값이지 킷의 규정이 아니다** — 당신 기기에서 다시 재라.

## 이 문서를 펴야 할 증상

- 아티팩트 발행이 `ECONNRESET`·타임아웃으로 끊긴다
- 클로드 앱이 「API 연결 실패」를 반복한다 (특히 대화가 길어질수록 잦아진다)
- `check_publish`(E6)가 통과도 실패도 아닌 **판정 불가**를 낸다
- 작은 파일은 멀쩡한데 **큰 것만** 안 올라간다

공통점은 하나다 — **킷의 파이썬 도구는 전부 정상**이고 네트워크 경계에서만 깨진다.
`python tools/selftest.py` 가 통과하는데 발행이 안 되면 이 문서가 맞다.

---

## 0. 첫 동작 — 원인의 성격부터 가른다

```bash
python tools/check_uplink.py --target-mb 3.0
```

E9 게이트가 크기 사다리(64KB→3MB)를 올리며 **버스트 붕괴인지 좁은 상행인지** 가른다.
종료코드는 `0` 통과 / `1` 못 올림 / `2` 판정 불가다.

| 사다리 모양 | 뜻 | 다음 절 |
|---|---|---|
| 작은 단은 빠른데 특정 크기부터 무너짐 | **버스트 붕괴** — 회선·랜카드는 결백하다 | §1 |
| 전 구간이 고르게 느림 | 실제로 상행이 좁다 | §3 |
| 최소 단(64KB)조차 못 감 | 판정 불가 — 망 단절·종단 장애 | §3 |

**호 크기부터 깎지 마라.** 킷의 판형 상한(D8)은 편집 규율이고, 한 기기의 사정에
맞춰 내리면 전 설치본이 판형을 잃는다. 원인을 없애는 것이 정공법이다.

## 1. 버스트 붕괴 — macOS 송신 버퍼 (유일한 확정 사례)

### 증상

대역은 충분한데 **한꺼번에 밀면** 끊긴다. 판별법이 명쾌하다 — 같은 파일을
**일부러 늦춰서** 보내면 완주한다:

```bash
# 1MB 를 무제한으로 → 죽는다면
curl -o /dev/null -X POST --data-binary @1mb.bin https://speed.cloudflare.com/__up
# 같은 1MB 를 1MB/s 로 → 완주한다면 버스트 붕괴다
curl -o /dev/null --limit-rate 1000k -X POST --data-binary @1mb.bin https://speed.cloudflare.com/__up
```

느려서 못 가는 것이라면 늦추면 **더** 오래 걸릴 뿐 완주 여부는 안 바뀐다.
늦춰서 되면 대역 문제가 아니다.

### 확인 — 자격 없이 읽을 수 있다

```bash
sysctl net.inet.tcp.autosndbufmax
```

`4194304`(4MB)이면 이것이 원인일 수 있다. macOS 는 송신 버퍼를 4MB 까지 자동
확장하는데, 그 값이 한꺼번에 나가면서 상행 입구의 큐를 넘긴다.

### 조치

```bash
sudo sysctl -w net.inet.tcp.autosndbufmax=262144
```

낮춘 뒤 §0 의 게이트를 **다시 돌린다.** 통과하면 확정이다.

**재부팅하면 기본값(4MB)으로 돌아간다.** 맥을 상시 켜두는 운용이면 그대로 두면 되고,
재부팅이 잦으면 부팅 시 적용되는 LaunchDaemon 을 만든다 — 다만 그것은 **그 기기의
설정이지 킷의 규정이 아니다.** 킷은 이 값을 배포하지 않는다.

### 실측 (2026-08-16 · Mac mini Mac16,10 · macOS 26.3.1)

| 무제한 업로드 | `autosndbufmax` 4MB | 256KB |
|---|---|---|
| 1MB | 15.04초에 ECONNRESET | 0.11초 · 9.5 MB/s |
| 2MB | 사망 | 0.19초 · 11.2 MB/s |
| 3MB | 사망 | 0.28초 · 11.4 MB/s |
| 10MB | 사망 | 0.88초 · 12.0 MB/s |

4MB 로 되돌리자 증상이 재발했고 256KB 로 다시 낮추자 사라졌다(A/B/A).

### 대가 — 알고 쓰라

단일 연결 최대 처리량이 `버퍼 ÷ RTT` 로 제한된다.

| 목적지 RTT | 256KB 천장 |
|---|---|
| 5ms (국내 CDN 엣지) | 약 51 MB/s — 가정용 회선보다 훨씬 높아 무영향 |
| 50ms | 약 5 MB/s |
| 150ms (원거리 직결) | 약 1.7 MB/s — 여기서만 손해가 난다 |

킷이 붙는 종단(Anthropic·claude.ai·GitHub·DART·국내 매체)은 대부분 국내 엣지에
잡혀 RTT 가 한 자릿수 ms 다. 그 범위에서는 잃는 것이 없다.

### 왜 이 증상은 「인터넷이 느리다」로 오진되는가

**선택적으로만 깨지기 때문이다.** 같은 기기에서 나머지는 전부 멀쩡하다:

| 작업 | 실측 |
|---|---|
| 하행(다운로드) | 6.2 MB/s 정상 |
| LAN 양방향 | 11.7 MB/s 정상 |
| 웹 브라우징 · DART RSS · GitHub · WebFetch | 정상 |
| 512KB 이하 업로드 | 정상 |
| **1MB 이상 단일 업로드** | **사망** |

평소 쓰는 것 중 **상행으로 수 MB 를 한 덩어리로 미는 작업이 거의 없다.** 브라우징도
다운로드도 스트리밍도 전부 하행이고, 대용량 업로드는 대개 청크로 쪼개 올린다.

그런데 이 킷과 클로드 코드는 정확히 그 조건을 만든다:
- **클로드 코드는 매 요청마다 대화 맥락 전체를 한 덩어리로 올린다** — 대화가 길어질수록
  덩어리가 커져 어느 순간 임계를 넘는다. 초반엔 멀쩡하다가 갈수록 자주 끊긴다면 이것이다
- **아티팩트 발행은 호 전체를 한 번에 올린다** — 오디오를 실은 호는 곧바로 MB 단위다

그래서 사용자에게는 「클로드만 이상하고 인터넷은 멀쩡하다」로 보이고, 원인 추적이
회선·앱·계정 쪽으로 새기 쉽다. **다른 것이 멀쩡한 것은 반증이 아니라 이 증상의 특징이다.**

### 이 처방의 한계 — 정직하게

- **공개 선례가 1건뿐이다** (2026-06, 독일 DSL · RTT 22ms). Apple 이 인정한 이슈가 아니다.
  다만 그 1건도 **클로드 코드 사용자**였고 처방이 글자 단위로 같다 — 사례가 드문 것은
  버그가 드물어서가 아니라 **이 조건을 밟는 작업이 드물기 때문**으로 보인다.
- **주류 튜닝 문서는 이 값을 올리라고 권한다** (ESnet 32MB 등). 통념에 반하는 처방이다.
- **왜 그 기기에서 터졌는지는 미규명이다.** 저지연 경로라서 더 잘 터진다는 설명은
  추론이고 뒷받침하는 문헌이 없다 — ESnet 은 오히려 반대로 서술한다.
- 그러므로 이 문서가 말하는 것은 **「그 기기에서 이 값이 증상을 켜고 껐다」까지**다.
  당신 기기에서 안 통하면 §2 로 간다.

### 배제해 둔 경쟁 가설

같은 OS·같은 기종군에 **Tahoe 26.x ECN 업로드 스톨** 보고가 있다
(처방 `sudo sysctl -w net.inet.tcp.ecn_initiate_out=0`). 증상 모양이 거의 같아
헷갈리기 쉽다. 가르는 법은 **ECN 을 끈 채로 고정하고 버퍼만 오가게** 하는 것이다 —
증상이 버퍼를 따라 움직이면 버퍼가 원인이다. 위 실측 기기에서는 그렇게 갈렸다.
당신 기기에서는 반대로 나올 수 있으니 **둘 다 재라.**

## 2. 버스트 붕괴 — 경로상 셰이퍼

§1 의 버퍼 조치로 안 되면 경로를 본다. 순서대로 좁힌다.

**⑴ 총량인지 연결당인지** — 업로드 3개를 동시에 띄운다. 합이 단일과 같으면
기기 단위로 걸린 제한이다.

**⑵ 유선·무선 동시** — 두 인터페이스는 MAC 도 IP 도 다르다. 그런데도 합이 단일과
같으면 원인이 MAC/IP 가 아니다. **랜선·IP 교체는 헛수고다.**
(주의: 송신 버퍼가 원인이어도 이 결과가 나온다 — 두 인터페이스가 같은 커널을 쓴다.
이 시험만으로 셰이퍼를 확정하지 마라.)

**⑶ 기기 쪽 셰이퍼** (자격 필요)

```bash
sudo dnctl list                    # dummynet 파이프 — 나오면 확정
sudo pfctl -s info | grep dummynet # 카운터가 0 이면 pf 는 셰이핑을 안 하고 있다
sudo pfctl -sr                     # 전역 규칙
sudo /usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
```

Network Link Conditioner 를 켠 채 잊는 사고가 흔하다 (시스템 설정 > 개발자).

**⑷ 망 쪽** — 공유기 관리화면의 QoS·트래픽 관리에서 그 기기 항목을 확인한다.
또는 **휴대폰 핫스팟에 붙여 §0 을 재현**한다 — 거기서 멀쩡하면 원인은 원래 망에 있다.
이 방법은 자격 없이 기기/망을 가른다.

## 3. 좁은 상행 — 실제로 대역이 모자란 경우

사다리 전 구간이 고르게 느리면 그때는 진짜다. 회선·랜포트·케이블을 먼저 보고,
전부 정상인데도 좁으면 **그때** 호 크기(`config.yaml` 의 `tts.embed`)를 논한다.

호 크기 계산은 `오디오 MP3 크기 × 1.34 + 지면` 이다(base64 가 4/3 로 부푼다).
비트레이트를 내리면 선형으로 줄지만, **48k 미만은 사람이 듣기 어렵다**(청취 실측).
그 아래로 내려야 발행되는 회선이면 크기가 아니라 회선을 고치는 게 맞다.

## 4. Cloudflare 봇 차단 — E6 판정 불가

### 증상

`check_publish`(E6)가 실패도 통과도 아닌 **판정 불가(:2)** 를 내고, 응답 헤더에
`cf-mitigated: challenge` 가 잡힌다.

### 원인

익명 판정은 쿠키 없고 JS 안 도는 `urllib` 요청인데 — 그게 정확히 로그아웃 독자를
흉내 내는 올바른 방법이다 — Cloudflare 가 그 모양을 봇으로 보고 막는다.
**아티팩트나 공유 설정과 무관하다.** `claude.ai` 도메인 전반에서 걸린다.

### 대응

게이트가 오판하지 않고 강등한 것이므로 **이것은 정상 동작이다.** 절차는:

1. 소유자가 브라우저에서 공유 상태를 **직접** 확인한다 (Share → General access 가
   `Anyone with the link` 인지, Shared version 이 최신인지)
2. run_log 종료 줄에 `"check_publish:2"` 와 함께 `reason` 에 형식대로 적는다:
   `수동 확인 마감 <YYYY-MM-DD HH:MM> check_publish — 확인 경위`
3. `check_run` 이 그 형식을 읽어 날짜를 닫는다

`check_run` 은 이 통과를 **「기계 판정이 아니라 형식 봉인」**이라고 출력에 명시한다.
회선이 바뀌어 익명 조회가 되면 `:0` 으로 재판정해 기록을 갱신한다.

## 5. 진단할 때의 규율

이 건에서 워커가 세 번 틀렸고, 그 세 번이 전부 같은 실수였다.

**⑴ 「느리다」와 「죽는다」를 먼저 가른다.** 첫 진단이 「상행 85KB/s 의 느린 회선」
이었는데, 그 85KB/s 는 **고장 난 상태를 잰 값**이었다. 실제 회선은 10~12MB/s 다.
속도 사다리(`--limit-rate` 를 바꿔가며 같은 크기)를 먼저 돌렸으면 첫날에 갈렸다.

**⑵ 증상이 사라진 것과 원인을 찾은 것은 다르다.** 「고치니 됐다」는 여러 원인과
양립한다 — 인플라이트를 줄이면 다른 경로의 증상도 함께 가려진다. 경쟁 가설을
**끄고 고정한 채** 변수 하나만 오가게 해야 갈린다.

**⑶ 판별력 없는 근거를 근거로 쓰지 않는다.** 「같은 공유기의 Windows 는 정상」을
버퍼 가설의 증거로 썼는데, Windows 는 ECN 을 기본으로 꺼서 **두 가설 모두** 그
관찰을 설명한다. 양쪽이 다 설명하는 사실은 아무것도 가르지 못한다.

**⑷ 진단 부하가 증상을 악화시킨다.** 대용량 업로드를 반복하는 진단 자체가 좁은
상행을 점유해 세션을 더 자주 끊었다. 재보기 전에 앞 시험이 끝났는지 확인한다.
